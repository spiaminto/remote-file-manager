파일매니저 접속 경계

밖의 브라우저에서 C:\_workspace의 파일까지 요청이 어떤 경계를 지나는지, 각 경계를 누가 지키는지 그린 도식이다. 위는 지금 추천하는 A안(Cloudflare Tunnel + Access), 아래는 비교용 B안(공유기 포트포워딩)이다.

A안 Cloudflare Tunnel + Access

  1. 밖의 브라우저가 files.spiaminto.com에 HTTPS로 접속한다. 주소와 인증서는 Cloudflare가 맡는다.
  2. 요청은 Cloudflare에서 멈추고 Access가 받는다. 홈서버는 아직 아무것도 받지 않았다.
  3. 로그인 쿠키가 없으면 Google 로그인으로 보낸다. 로그인한 이메일이 허용 목록의 하나와 다르면 여기서 끝난다.
  4. 통과한 요청에 Cf-Access-Authenticated-User-Email 헤더가 붙어 터널로 간다. 요청 하나가 100MB를 넘으면 여기서 413으로 막힌다.
  5. 터널은 홈서버의 cloudflared가 Cloudflare 쪽으로 먼저 맺어 둔 연결이다. 요청은 이 연결을 거꾸로 타고 들어오므로 공유기에 열린 포트가 없어도 된다.
  6. cloudflared가 같은 PC의 FBQ(127.0.0.1)로 넘긴다.
  7. FBQ가 헤더의 이메일로 사용자를 확인하고, 루트 안에서만 읽고 쓴다.

B안 공유기 포트포워딩 (비교용)

통신사가 공인 IP를 주지 않는 회선이면 B안은 할 수 없다. 사용자의 회선은 확인하지 않았다.

FBQ의 책임은 두 안에서 같다. 파일을 어떻게 보여 주고 무엇을 허용하는지다. 달라지는 것은 FBQ 앞에 무엇이 서느냐다. A안은 Cloudflare가 주소, 인증서, 로그인, 걸러 내기를 맡고, B안은 그 넷이 사용자와 FBQ에게 넘어온다.

확인하지 않은 것과 받아들이는 위험

  • FBQ를 127.0.0.1에만 열고 Google OIDC를 쓰는 설정 이름은 에이전트의 지식이다. 설치하면서 확인한다.
  • A안에서 같은 PC의 다른 프로그램은 127.0.0.1로 FBQ에 접속해 이메일 헤더를 꾸며 보낼 수 있다. FBQ는 헤더를 그대로 믿기 때문이다. 사용자 혼자 쓰는 PC라 받아들이는 위험으로 본다.
  • Tunnel 공개 호스트명에 100MB가 걸린다는 것은 Cloudflare의 두 문장을 이어서 추정한 것이다.
